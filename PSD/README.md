# PSD — бизнес-требования тренажёра

Здесь живут требования к приложению: что должен видеть и делать ученик и почему. Код и спеки
OpenSpec выводятся из этих документов. Это единственное место, где требования правятся.

## Что где лежит

```
PSD/
  README.md                 — этот файл: структура, процесс, правила
  Patterns/                 — шаблоны и инструкции (общие с другими проектами владельца)
  patterns/                 — шаблоны артефактов OpenSpec (intend, proposal)
  specifications/
    M-XX/                   — модуль
      M-XX Паспорт модуля.md  — состав модуля, статусы, связь с OpenSpec, беклог
      C-XX-N Название.md      — спецификация компонента
```

Главные шаблоны:
- [Спецификация компонента](<Patterns/ШАБЛОН — Спецификация компонента.md>)
- [Паспорт модуля](<Patterns/ШАБЛОН — Паспорт модуля.md>)

Блоки с пометкой `(опц.)` заполняются, только если для них есть информация. Иначе блок удаляется
целиком, вместе с заголовком.

## PSD и OpenSpec: кто за что отвечает

- **PSD** — правда о намерении: чего хочет ученик и почему. Наблюдаемое поведение (OB), лимиты,
  решения, открытые вопросы.
- **`openspec/specs/`** — правда о реализации: нормативный контракт системы, выведенный из PSD.
  Меняется только через change OpenSpec.
- Связь между ними — колонка «Capability OpenSpec» в паспорте модуля и строка «Источник требований —
  C-XX-N» в каждой спеке OpenSpec.

Изменение поведения всегда начинается с правки спецификации в PSD, а не со спеки OpenSpec.

## Процесс: от идеи до кода

1. **Спецификация.** Владелец, Claude или вместе пишут `C-XX-N Название.md` по шаблону прямо в
   папку модуля. Статус `draft`.
2. **Паспорт.** В том же коммите в паспорт модуля добавляется строка компонента:
   спецификация `draft`, реализация «не начата». Новый модуль — новая папка, паспорт по шаблону и
   строка в таблице «Модули» выше.
3. **`/opsx:explore`.** Спецификация сверяется с кодом, CLAUDE.md и соседними спеками. Итог
   explore — всегда коммит в спецификацию: решения в «Приложение Б», оставшиеся вопросы в
   «Приложение В». Когда вопросов нет, статус — `ready` (и в спеке, и в паспорте).
4. **`/opsx:propose <change>`** по готовой спецификации. Владелец ревьюит `openspec/changes/<change>/`.
   Паспорт: «в работе, change `<имя>`».
5. **`/opsx:apply <change>`** — код. Решение, принятое по ходу работы и меняющее видимое поведение,
   попадает в спецификацию (Приложение Б) **тем же PR**.
6. **PR** → владелец проверяет на планшете → слияние.
7. **`/opsx:archive <change>`** — спеки OpenSpec синхронизируются. Паспорт: «реализована,
   change `<имя>`», колонка «Capability OpenSpec» заполнена.

Один change = одна спецификация (или её часть) = один пункт плана CLAUDE.md §10 = один PR.

## Правила

- **Имена файлов:** `C-XX-N Название.md`, `M-XX Паспорт модуля.md`. Код в начале имени, дальше —
  по-русски, как в заголовке документа.
- **Номера не переиспользуются:** удалённые OB, LIM, Р, C-XX-N не занимаются повторно.
- **Статус спецификации** (`draft` / `ready`) — про готовность текста. Реализация — отдельная
  колонка паспорта, чтобы не держать один факт в двух местах.
- **Числа** — в «Приложении А. Лимиты», в тексте только ссылки `[→ LIM-n]`.
- **Паспорт обновляется** в том же коммите, что и спецификация, и при архивации change'а.
