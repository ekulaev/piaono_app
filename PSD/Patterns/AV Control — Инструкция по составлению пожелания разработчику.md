# AV Control — Инструкция по составлению пожелания разработчику

Справочный документ. Описывает, как переводить продуктовую спецификацию компонента в пожелание для разработчика (Dev-документ), какой у него обязательный минимум, и как проверять готовый текст на соответствие стилю.

---

## 1. Что такое пожелание и зачем оно нужно

Пожелание — это мост между продуктовой спецификацией (что должно происходить, с точки зрения пользователя и продукта) и задачей в трекере (что конкретно закодировать и как это проверить на стенде).

Спецификация описывает поведение через Observable Behaviors — она не решает, каким механизмом это будет реализовано. Пожелание разворачивает эти OB в конкретные сценарии, структуры данных, ошибки и граничные случаи, но **тоже не выбирает конкретную технологию** — выбор технологии (протокол, формат сериализации, конкретные числовые пороги) остаётся за техлидом.

Простыми словами: спецификация говорит «канал должен быть защищён и уведомлять об обрыве». Пожелание говорит «вот шесть типов сообщений, вот порядок при подключении, вот что считается обрывом, вот критерии сдачи». Ни спецификация, ни пожелание не говорят «используй WebSocket» — это решает техлид.

---

## 2. Что пожелание делает и чего не делает

| Делает | Не делает |
| --- | --- |
| Разворачивает OB спецификации в конкретные сценарии и правила | Не придумывает новый scope, которого нет в спецификации |
| Явно разделяет «уже решено продуктом» и «остаётся решить техлиду» | Не выбирает технологию/протокол/формат за техлида |
| Даёт проверяемые критерии сдачи (Definition of Done) | Не пересказывает конкурентный анализ — для этого есть отдельный аудит |
| Ссылается на ID источника (OB-\*, NFR-\*, US-\*, LIM-\*) | Не мотивирует и не продаёт идею — читатель уже знает, зачем это нужно |
| Явно помечает нерешённые границы между компонентами | Не решает такие границы молча, по своему усмотрению |

## 3. Базовый минимум: что обязательно должно быть в документе

1. **Метаданные** — компонент, для кого документ (роль читателя), тип задачи, приоритет, ссылка на задачу/эпик.
2. **Цель одной фразой** — что именно должно заработать в результате, без вступлений.
3. **Что реализовать** — по блокам (например: подключение, контракт сообщений, обрыв/keep-alive, контроль прав, наблюдаемость/диагностика). Каждый блок — конкретные правила, не описание пользы.
4. **Контракт данных/сообщений**, если применимо — таблица: тип · направление · смысл. Без этого раздела разработчик додумывает форматы сам.
5. **Сценарии поведения** — пошагово, по схеме «дано → действие → результат» или простой нумерованный список шагов, для каждого ключевого потока (подключение, основной сценарий, отказ, граничный случай).
6. **Вне scope** — что сознательно не делается в этой задаче и почему (одна короткая причина на пункт, не абзац).
7. **Технические развилки** — явный список того, что уже решено продуктом, и отдельно — что остаётся выбрать техлиду/разработчику.
8. **Зависимости** — что нужно от других компонентов/людей, что эта задача разблокирует.
9. **Критерии сдачи (DoD)** — проверяемые на стенде пункты, без общих слов вроде «работает нормально».
10. **Открытые вопросы** — если граница со спецификацией или с другим компонентом не решена, это фиксируется явно, а не замалчивается.

Необязательно, но допустимо коротким блоком: типичные ошибки реализации, список артефактов на выходе.

**Не включать в базовый минимум:** конкурентное сравнение, риски (если не критичны для этой конкретной задачи), распределение ролей/RACI, мотивационные истории пользователя — для всего этого есть другие документы.

## 4. Правила языка и оформления

| Правило | Плохо | Хорошо |
| --- | --- | --- |
| Простой технический язык, без риторики | «Без этой задачи нет смысла в кнопке на панели» | «Канал — обязательное условие для передачи команд с панели» |
| Императив вместо описательности | «Нужно, чтобы канал обрабатывал разрывы» | «Канал обрабатывает разрыв соединения» |
| Единая терминология на весь документ | «Обрыв» в одном месте, «разрыв связи» и «потеря соединения» в других | Один термин закреплён и используется везде одинаково |
| Английские термины поясняются при первом употреблении | «keep-alive» без пояснения | «keep-alive (контрольный сигнал поддержания соединения)» |
| Жирный шрифт — только для терминов при первом определении или критических предупреждений | Жирным выделена половина текста | Жирный используется точечно, 1–2 раза на абзац максимум |
| Таблицы — для однородных сравнимых атрибутов | Список типов сообщений текстом в абзаце | Таблица: тип · направление · смысл |
| Нумерованные списки — для последовательных шагов | Шаги подключения перечислены через запятую в одном предложении | Шаги пронумерованы по порядку выполнения |
| Маркированные списки — для неупорядоченных пунктов | Нумерация там, где порядок не важен | Маркеры для не последовательных пунктов |
| Единая вложенность заголовков | Скачок с `##` сразу на `####` | Последовательная вложенность `##` → `###` |
| Короткие абзацы, одна мысль на абзац | Абзац на 6 предложений с разными темами | Абзац на 1–3 предложения, одна тема |
| Без сравнений с конкурентами и маркетинговых оборотов | «Это не просто ещё один WebSocket» | Раздел просто не содержит подобных фраз |

## 5. Промт для ИИ — генерация или проверка документа

Промт универсальный: работает и для составления пожелания с нуля по спецификации, и для проверки/приведения к стилю уже готового текста. Вставляется в начало задачи ИИ вместе с приложенной спецификацией (и, если есть, черновиком пожелания).

```
Ты помогаешь составить или проверить "пожелание разработчику" (Dev-документ) на основе продуктовой спецификации компонента AV Control.

Контекст:
- Продуктовая спецификация — источник истины. Она описывает поведение через Observable Behaviors (OB), не выбирает технологию реализации.
- Пожелание разворачивает OB в конкретные сценарии, контракты данных и критерии сдачи, но тоже не выбирает технологию — выбор протокола/формата/числовых порогов остаётся за техлидом.
- Если в задаче приложена спецификация без готового пожелания — составь пожелание с нуля.
- Если приложен черновик пожелания — проверь его и перепиши в соответствии с правилами ниже, сохранив весь продуктовый смысл; не добавляй нового scope и не убирай существующий без явного указания на несоответствие спецификации.

Обязательные разделы документа:
1. Метаданные (компонент, для кого, тип задачи, приоритет, эпик/задача)
2. Цель одной фразой
3. Что реализовать — по функциональным блокам
4. Контракт данных/сообщений (таблица: тип · направление · смысл), если применимо
5. Сценарии поведения по шагам для каждого ключевого потока
6. Вне scope — с краткой причиной на каждый пункт
7. Технические развилки — отдельно "уже решено продуктом" и "решает техлид/разработчик"
8. Зависимости
9. Критерии сдачи (DoD) — проверяемые на стенде, без общих формулировок
10. Открытые вопросы — если граница с другим компонентом или со спецификацией не зафиксирована однозначно, вынеси это явно отдельным пунктом, не решай самостоятельно

Не включай: сравнение с конкурентами, риски (если не критичны для конкретной задачи), распределение ролей/RACI, мотивационные истории пользователя.

Правила языка и оформления:
- простой технический язык, императив, без риторических оборотов и метафор
- единая терминология на весь документ — один термин на одно понятие
- английские термины поясняются в скобках при первом употреблении
- жирный шрифт только для терминов при первом определении или критических предупреждений, не как декоративное выделение
- таблицы — для однородных сравнимых атрибутов; нумерованные списки — для последовательных шагов; маркированные — для неупорядоченного
- последовательная вложенность заголовков без пропуска уровней
- короткие абзацы, одна мысль на абзац

Если в приложенной спецификации есть пункты Observable Behavior, не имеющие явного отражения в пожелании (или наоборот — пожелание описывает поведение, отсутствующее в спецификации), укажи это отдельным списком расхождений в конце ответа, не исправляя спецификацию и не додумывая её самостоятельно.

Выведи готовый документ полностью в Markdown, готовый к вставке в файл.
```

---

## Как этим пользоваться

Промт из раздела 5 — рабочий инструмент, вставляется целиком в чат вместе со спецификацией (и черновиком пожелания, если он уже есть у аналитика). Разделы 3–4 — чек-лист для быстрой ручной проверки готового документа глазами, без ИИ.
