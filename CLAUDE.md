# CLAUDE.md — Нотный тренажёр (sight-reading trainer)

> Персональный проект. Владелец — взрослый ученик пианино со слабым зрением,
> бывший fullstack-веб-разработчик (навыки подзабыты, свободно **читает** код,
> хочет разобраться, как всё устроено). Работа ведётся через Claude Code on the web
> (браузер + GitHub + GitHub Pages). Общайся с владельцем и пиши описания PR по-русски.

---

## 1. Что это и зачем

Тренажёр чтения нот с листа. Цифровое пианино подключается к планшету по **USB-MIDI**,
приложение показывает ноты на нотном стане, ученик играет — приложение проверяет
попадания в реальном времени.

**Главная проблема, которую решаем.** Типичные тренажёры (и текущий у владельца)
показывают по одной ноте и учат её *называть*. Это тренирует узнавание отдельных
символов, но не превращается в беглость. Беглое чтение — это чтение **в потоке**:
расстояний между нотами (интервалов), узнаваемых фигур, ритма. Поэтому мы читаем
**последовательностями** и **интервалами от опорных нот**, а не изолированные ноты.

**Чего проект НЕ делает.** Никакой авторизации, аккаунтов, аналитики, серверов, базы
данных, внешних API, монетизации. Всё локально, на устройстве. Это MVP-инструмент,
а не платформа.

---

## 2. Приоритеты (строго в этом порядке)

1. **Надёжность MIDI-соединения.** Тренажёром пользуются каждый день с реальным
   железом. Если приложение «не видит пианино» — привычка умирает. Это приоритет №1.
2. **Читаемость при слабом зрении.** Крупно, контрастно, ничего тонкого и мелкого.
3. **Понятность кода.** Владелец читает код и хочет разобраться. Чёткие слои,
   понятные имена, минимум зависимостей.
4. **Простота.** MVP. Не усложнять, не добавлять фич сверх плана.

Когда приоритеты конфликтуют — выигрывает тот, что выше.

---

## 3. Технологический стек

- **PWA:** React + **TypeScript** + Vite.
- **Нотация:** VexFlow.
- **MIDI:** Web MIDI API (браузерный).
- **Оффлайн:** service worker (`vite-plugin-pwa` / Workbox).
- **Хранение:** `localStorage` (для MVP достаточно; без бэкенда).
- **Хостинг:** статическая сборка на **GitHub Pages** (HTTPS обязателен — без него
  Chrome не даст Web MIDI работать).
- **Целевая среда исполнения:** Chrome на Android-планшете. Ориентация — **ландшафт**
  основная, адаптив вплоть до телефона.
- **Запрещённые зависимости по умолчанию:** UI-киты, CSS-фреймворки-комбайны,
  state-менеджеры уровня Redux, что-либо серверное. Каждую новую библиотеку сверх
  списка выше — обосновать в описании PR перед добавлением.

## 4. Архитектура (обязательный паттерн)

Строгое разделение на слои, поток данных **однонаправленный**:

```
midi/     → engine/        → ui/
(железо)    (логика)         (React + отрисовка)
```

- **`midi/`** — единственное место, где есть сырой Web MIDI. Этот модуль:
  запрашивает доступ; перечисляет входы; выбирает устройство (если их несколько);
  подписывается на `statechange`; делает авто-реконнект; нормализует сообщения
  (note-on / note-off, при этом **velocity 0 = note-off**); игнорирует всё лишнее.
  Наружу отдаёт **только чистые типизированные события**, например:
  `NoteOn { pitch, velocity, time }`, `NoteOff { pitch, time }`,
  `ConnectionChange { state }`.
- **`engine/`** — логика упражнений: генерация последовательностей, проверка
  попаданий, гаснущие подсказки, адаптивность, статистика. Не знает про React
  и не знает про сырой MIDI — только про события из `midi/`.
- **`ui/`** — React-компоненты и отрисовка нот. **Никогда** не трогает сырой MIDI,
  работает только с событиями и с состоянием из `engine/`.

**Почему так:** (1) надёжность — логику соединения можно чинить и тестировать
изолированно; (2) понятность — владелец видит три ясных слоя, а не «всё во всём».

## 5. Контракт надёжности (приоритет №1)

- Отклик на сыгранную ноту виден за **≤ ~50 мс**. Обработка MIDI не должна блокировать
  отрисовку.
- **Все состояния соединения — явные и видимые:** нет доступа к MIDI / устройство не
  подключено / подключаемся / подключено / соединение потеряно. На экране всегда есть
  индикатор «пианино на связи».
- **Авто-реконнект после сна планшета.** После пробуждения приложение само
  восстанавливает связь (через `statechange`), ничего не требуя от пользователя.
- Если MIDI-устройств больше одного — дать выбрать из списка.
- **Оффлайн:** после первой загрузки всё работает без сети (service worker кеширует
  оболочку, шрифты, данные упражнений).
- **Никаких падений** на неожиданных MIDI-сообщениях: неизвестное игнорируем, не крешим.

## 6. Дизайн-конституция (приоритет №2)

**Тезис.** Это **прибор**, а не «дизайн». Ноты — единственный герой. Всё, что не ноты
и не обратная связь, должно исчезнуть. Референс — Дитер Рамс, тюнер, приборная
панель. **Не** маркетинговый лендинг.

**Стиль.** Воздушно, мягко, чуть тактильно (скруглённые углы, лёгкая глубина) — **но с
честным контрастом**. Мы взяли душу неоморфизма (воздух, мягкость) и выбросили его
механизм (низкий контраст, элемент цвета фона): низкий контраст несовместим со слабым
зрением.

### Обязательные требования под слабое зрение (это не «желательно»)

- Контраст текста — **цель 7:1 (WCAG AAA)**, не минимум 4.5.
- **Ничего тонкого:** вес шрифта 500–600, без ultra-light и волосяных линий.
  **Линии нотного стана — толще дефолта VexFlow** (дефолт «призрачит» на ретине).
- **Крупно по умолчанию:** базовый текст ≥ 18–20px, ноты — максимально крупно.
  Мелкие иконки не несут смысл в одиночку.
- Все размеры в `rem`; уважать системный зум; **не** ставить `user-scalable=no`;
  проверять с увеличенным системным шрифтом ОС.
- **Цели касания ≥ 56–64px** для основных действий (крупнее общего стандарта).
- **Обратная связь — крупными изменениями** (заливка / форма / положение) плюс цвет,
  **никогда** одним оттенком и не тонким штрихом (глаз ловит её боковым зрением).

### ЗАПРЕЩЕНО (признаки AI-дизайна и вредные для тренажёра эффекты)

- Фиолетовые / индиго градиенты, дефолтная палитра Tailwind (indigo-500 и компания),
  градиентный текст, градиентные заливки фона.
- Три AI-клише: кремовый фон + серифный дисплейный шрифт + терракота (~`#D97757`);
  почти-чёрный фон + один кислотный акцент; «газетная» вёрстка в тонкие линейки.
- Glassmorphism / матовое стекло; всё-в-карточках с мягкими тенями; бейджи-пилюли
  повсюду; скруглённое ВСЁ без меры.
- Эмодзи как иконки или заголовки разделов.
- «Атмосферный» тулкит: зерно, шум, градиентные сетки, кастомные курсоры,
  декоративные бордюры.
- Модные «характерные» дисплейные шрифты и игра пары дисплей+текст; Space Grotesk.
- **Любая декоративная анимация:** staggered-появления при загрузке, hover-флеши,
  scroll-эффекты, «красивые» переходы. В упражнении отклик **мгновенный (0–80мс)**.
- Прыгающая вёрстка (layout shift / CLS). Ноты и элементы не дёргаются.
- Модалки поверх упражнения. Маркетинговые паттерны (hero-секции, «01/02/03»,
  eyebrow-подписи), если они не кодируют реальную последовательность.

### Позитивные правила

- **Палитра (старт):** светлая тёплая «бумага» (не глянцево-белая, без блика), тёмные
  ноты поверх, **ровно один спокойный акцент** — только для «эту ноту играть сейчас».
  Тёмная тема — опция на потом. Финально калибруется на реальном планшете.
- **Шрифт:** один чистый читаемый UI-sans в продуманном масштабе (не модный
  дисплейный). Настоящая типографика здесь — **нотный SMuFL-шрифт (Bravura)** через
  VexFlow. Ноты и есть наш шрифт.
- **Компоновка:** один экран, **без скролла в упражнении**; ноты крупно по центру;
  управление крупное, редкое, по краям. Ландшафт основной; адаптив до телефона через
  `clamp()`, а не набор жёстких брейкпоинтов. Крупные цели **не ужимать** под телефон —
  уменьшать их количество и перекомпоновывать.
- **Тексты — с точки зрения ученика, простыми словами.** «Подключи пианино кабелем»,
  а не «MIDI device not found». Ошибка не извиняется и говорит, что делать. Кнопка
  называет действие: «Играть», не «Начать сессию».
- **Пол по доступности:** видимый фокус клавиатуры, `prefers-reduced-motion` уважается,
  контраст AAA.

## 7. Поведение упражнения (MVP = Тир 0 + Тир 1)

- **Единица упражнения:** последовательность из **3–8 нот по одной** (не аккорды),
  **один ключ за раз** (скрипичный ИЛИ басовый — на выбор), в небольшом диапазоне.
  Старт — 5-пальцевая позиция около до первой октавы (C4), диапазон расширяемый.
- **Тайминг: без таймера.** Ученик играет в своём темпе. Скорость реакции по каждой
  ноте замеряется **тихо** и идёт в адаптивность. Никакого обратного отсчёта и
  «провала». (Мягкий / жёсткий таймер — возможная опция в будущем, не в MVP.)
- **Основной режим (строим первым в Тире 1):** чтение последовательности с
  **якорем-подсказкой интервала**, которая **гаснет** по мере успехов (сначала показано
  «эта нота на терцию выше опорной», со временем подсказка убирается).
- **Дополнительные режимы Тира 1 (следом):** «только ритм» (высота фиксирована,
  выстукиваешь рисунок по любой клавише) и «только контур» (важно направление
  вверх/вниз/на месте, не точная нота).
- **Обратная связь (дублированная цветом + формой):** верно → нота «оседает» (крупное
  видимое изменение) и переход к следующей; мимо → ожидаемая нота пульсирует,
  неправильная остаётся в контуре, перехода нет, пока не сыграно верно, либо есть явная
  кнопка «Пропустить».
- **Адаптивность (MVP-простая):** по каждой ноте (pitch) и каждому интервалу копим в
  `localStorage` точность и время реакции; генератор чаще выдаёт слабые места.
  Полноценный SRS — потом.
- **Сессия:** N последовательностей (дефолт 10) → экран итога (точность, самые
  медленные ноты, что улучшилось) → «повторить» / «новая».
- **Настройки:** ключ(и), диапазон, длина последовательностей, вкл/выкл подсказок,
  светлая/тёмная тема (когда появится). Прогресс и настройки переживают перезапуск.

## 8. Все состояния экрана (реализовать, НЕ только happy path)

Нет доступа к MIDI · Пианино не подключено (+ как подключить, простыми словами) ·
Подключаемся · Готово, жду · Идёт упражнение · Верно · Мимо · Упражнение пройдено
(итог) · Ещё нет прогресса (пустой экран как приглашение начать) · Соединение потеряно
(идёт авто-реконнект).

Пустой экран — приглашение к действию, а не заглушка. Каждое состояние спроектировано.

## 9. Соглашения по коду (ради понятности владельцем)

- TypeScript со **строгими типами на границах** (особенно MIDI-события и модель
  упражнения). Типы документируют намерение.
- Понятные имена, небольшие функции. Комментарии там, где нужно объяснить **«почему»**,
  а не «что».
- Простая типизированная обёртка над `localStorage`, без разбросанных обращений.
- Prettier по умолчанию. Без хитрых абстракций «на вырост».

## 10. План по этапам (выполнять в этом порядке, по одному этапу на PR)

0. **MIDI-монитор** — первая задача, снимает главный риск. Минимальная страница: список
   подключённых MIDI-устройств + лог note-on/off в реальном времени (номер + имя ноты).
   Задеплоить на Pages, владелец проверяет на планшете с реальным пианино.
   **Не двигаться дальше, пока цепочка железа не подтверждена.**
1. Каркас PWA + service worker + оффлайн + деплой на Pages. Экран «жду пианино» со
   всеми состояниями соединения из раздела 8. Сюда же вошёл модуль `midi/` с событийным
   интерфейсом, авто-реконнектом и видимым индикатором связи.
2. Экранная клавиатура на 88 клавиш: показывает нажатия с пианино и силу нажатия,
   играет касанием как полноценный источник нот, прокрутка кнопками
   (спецификация C-KBD-1, change `add-piano-keyboard`).
3. Отрисовка ноты и последовательности через VexFlow по дизайн-правилам (крупно,
   толстые линии, контраст AAA).
4. Основной цикл: показать последовательность → играть → проверка → обратная связь →
   итог сессии.
5. Якорь + интервал с гаснущими подсказками.
6. `localStorage`: прогресс, настройки, простая адаптивность.
7. Режимы «только ритм» и «только контур».
8. Экраны настроек и статистики.

## 11. Как работать со мной (правила для Claude Code)

- Держи дизайн-скилл (frontend-design) в режиме **строгого минимализма** по
  конституции раздела 6. Никакой «атмосферы» и «фирменного элемента» — наш фирменный
  элемент это **читаемость и мгновенная обратная связь**, и ничего больше.
- Реализуй **все состояния** из раздела 8, а не happy path.
- Держи слои `midi → engine → ui` раздельно; UI не трогает сырой MIDI.
- Перед крупным архитектурным решением или новой зависимостью — **коротко объясни и
  предложи** в описании PR, не молча.
- Фичи ведутся по **OpenSpec** (spec-driven development): `/opsx:propose` → владелец
  ревьюит `openspec/changes/<имя>/` → `/opsx:apply` → `/opsx:archive`. Код не пишем, пока
  спека не согласована. Один change = один пункт плана = один PR.
- Каждый PR **маленький**, по одному пункту плана. В описании — по-русски: что сделал и
  **как проверить на планшете с пианино** (владелец тестирует MIDI вручную — в облаке
  железа нет).
- Перед сдачей PR — **проход самокритики**: убери всё, что не служит читаемости и
  надёжности (правило «убери один аксессуар»).
