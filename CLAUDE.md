# CLAUDE.md — Нотный тренажёр (sight-reading trainer)

> Персональный проект. Владелец — взрослый ученик пианино со слабым зрением,
> бывший fullstack-веб-разработчик (навыки подзабыты, свободно **читает** код,
> хочет разобраться, как всё устроено). Работа ведётся через Claude Code on the web
> (браузер + GitHub + GitHub Pages). Общайся с владельцем и пиши описания PR по-русски.

---

## 1. Что это и статус

Тренажёр чтения нот с листа. Цифровое пианино подключается к планшету по **USB-MIDI**,
приложение показывает ноты на нотном стане, ученик играет — приложение проверяет попадания
в реальном времени.

**Статус: MVP готов, идёт развитие.** Владелец занимается с тренажёром каждый день, на устройстве
накоплены его настройки и прогресс. Отсюда главное правило фазы развития: **не ломать привычное.**
Поведение существующей фичи меняется только через спецификацию (раздел 9), а не попутно.

**Продуктовые принципы** — на них опирается любая новая фича:

- **Читаем потоком.** Беглость — это последовательности, интервалы от опорных нот, контур,
  ритм, а не называние отдельных нот.
- **В своём темпе.** Без обратного отсчёта и «провала»; скорость реакции замеряется тихо.
- **Обратная связь — цветом и формой одновременно**, крупно, мгновенно.
- **Адаптивность тихая.** Трудные места выпадают чаще, ученик видит, что стало лучше.
- **Пустой экран — приглашение к действию**, а не заглушка.

**Чего проект НЕ делает.** Никакой авторизации, аккаунтов, аналитики, серверов, базы
данных, внешних API, монетизации. Всё локально, на устройстве.

## 2. Приоритеты (строго в этом порядке)

1. **Надёжность MIDI-соединения.** Тренажёром пользуются каждый день с реальным
   железом. Если приложение «не видит пианино» — привычка умирает. Это приоритет №1.
2. **Читаемость при слабом зрении.** Крупно, контрастно, ничего тонкого и мелкого.
3. **Понятность кода.** Владелец читает код и хочет разобраться. Чёткие слои,
   понятные имена, минимум зависимостей.
4. **Простота.** Не усложнять, не добавлять фич сверх спецификации.

Когда приоритеты конфликтуют — выигрывает тот, что выше.

## 3. Стек и инструменты

- **PWA:** React + **TypeScript** + Vite; оффлайн — `vite-plugin-pwa` (Workbox).
- **Нотация:** VexFlow (шрифт Bravura).
- **MIDI:** Web MIDI API (браузерный).
- **Хранение:** `localStorage` через обёртку `src/storage/` (раздел 7).
- **Проверки:** Vitest (тесты), oxlint (линтер), Prettier (`.prettierrc`).
- **Хостинг:** статическая сборка на **GitHub Pages**, base `/piaono_app/` (HTTPS обязателен —
  без него Chrome не даст Web MIDI работать). Слияние в `main` сразу деплоится на планшет
  владельца; новая версия подхватывается кнопкой «Обновить».
- **Целевая среда:** Chrome на Android-планшете, ландшафт — основная ориентация; адаптив вплоть
  до телефона.
- **Запрещённые зависимости по умолчанию:** UI-киты, CSS-фреймворки-комбайны,
  state-менеджеры уровня Redux, что-либо серверное. Каждую новую библиотеку — обосновать в
  описании PR перед добавлением.

Команды:

| Команда | Что делает |
|---|---|
| `npm run dev` | Dev-сервер: `http://localhost:5173/piaono_app/` |
| `npm run build` | Проверка типов + сборка |

| `npm test` | Vitest |

## 4. Архитектура (обязательный паттерн)

Строгое разделение на слои, поток данных **однонаправленный**:

```
midi/     → engine/        → ui/
(железо)    (логика)         (React + отрисовка)
                 ↕
             storage/
         (данные на устройстве)
```

- **`midi/`** — единственное место, где есть сырой Web MIDI: доступ, входы, выбор устройства,
  `statechange`, авто-реконнект, нормализация (note-on / note-off, **velocity 0 = note-off**),
  всё лишнее игнорируется. Наружу — **только чистые типизированные события**
  (`NoteOn`, `NoteOff`, `ConnectionChange`).
- **`engine/`** — логика упражнений: генерация, проверка попаданий, подсказки, адаптивность,
  статистика. Не знает про React и про сырой MIDI.
- **`storage/`** — единственное место, где есть `localStorage`: типизированное чтение и запись
  настроек и прогресса.
- **`i18n/`** — переводы (один файл на язык, код языка в имени), выбор языка, формы числительных, форматы чисел и дат. Чистый слой без React: `engine/` и `midi/` слов не знают — отдают идентификаторы и числа, слова подставляет `ui/`.
- **`ui/`** — React-компоненты и отрисовка нот. **Никогда** не трогает сырой MIDI и
  `localStorage` напрямую.

**Общие механизмы UI — переиспользуй, не пиши заново:**

| Что | Где |
|---|---|
| Кнопка «?» и окно подсказки; тексты подсказок — одна запись в `hints.ts` | `ui/hints/` |
| Диалог подтверждения «Да / Нет» для критичных действий | `ui/ConfirmDialog.tsx` |
| Шапка экрана: «Назад», «Домой», заголовок | `ui/ScreenHeader.tsx` |
| Верхняя панель: статус связи, «Прогресс», «Настройки», «Обновить» | `ui/topbar/` |
| Выбор из вариантов, счётчик, флажок | `ui/controls/Controls.tsx` |
| Значки (линейные SVG) | `ui/icons/Icons.tsx` |
| Тексты на языках: файлы перевода `src/i18n/locales/<язык>.ts`, поиск текста `useT()` | `src/i18n/`, `ui/i18n/` |

## 5. Контракт надёжности (приоритет №1)

- Отклик на сыгранную ноту виден за **≤ ~50 мс**. Обработка MIDI не должна блокировать
  отрисовку.
- **Все состояния соединения — явные и видимые:** нет доступа к MIDI / устройство не
  подключено / подключаемся / подключено / соединение потеряно. На экране всегда есть
  индикатор «пианино на связи».
- **Авто-реконнект после сна планшета.** После пробуждения приложение само
  восстанавливает связь (через `statechange`), ничего не требуя от пользователя.
- Если MIDI-устройств больше одного — дать выбрать из списка.
- **Оффлайн:** после первой загрузки всё работает без сети (service worker кеширует
  оболочку, шрифты, данные упражнений, картинки подсказок).
- **Никаких падений** на неожиданных MIDI-сообщениях: неизвестное игнорируем, не крешим.

## 6. Дизайн-конституция (приоритет №2)

**Тезис.** Это **прибор**, а не «дизайн». Ноты — единственный герой. Всё, что не ноты
и не обратная связь, должно исчезнуть. Референс — Дитер Рамс, тюнер, приборная
панель. **Не** маркетинговый лендинг.

**Стиль.** Воздушно, мягко, чуть тактильно (скруглённые углы, лёгкая глубина) — **но с
честным контрастом**. Мы взяли душу неоморфизма (воздух, мягкость) и выбросили его
механизм (низкий контраст, элемент цвета фона): низкий контраст несовместим со слабым
зрением.

### Обязательные требования под слабое зрение (это не «желательно»)

- Контраст текста — **цель 7:1 (WCAG AAA)**, не минимум 4.5.
- **Ничего тонкого:** вес шрифта 500–600, без ultra-light и волосяных линий.
  **Линии нотного стана — толще дефолта VexFlow** (дефолт «призрачит» на ретине).
- **Крупно по умолчанию:** базовый текст ≥ 18–20px, ноты — максимально крупно.
  Мелкие иконки не несут смысл в одиночку.
- Все размеры в `rem`; уважать системный зум; **не** ставить `user-scalable=no`;
  проверять с увеличенным системным шрифтом ОС. **Корневой шрифт — 18px: `1rem` = 18px**,
  но в медиазапросах `rem` считается от 16px.
- **Цели касания ≥ 56–64px** для основных действий (крупнее общего стандарта).
- **Обратная связь — крупными изменениями** (заливка / форма / положение) плюс цвет,
  **никогда** одним оттенком и не тонким штрихом (глаз ловит её боковым зрением).

### ЗАПРЕЩЕНО (признаки AI-дизайна и вредные для тренажёра эффекты)

- Фиолетовые / индиго градиенты, дефолтная палитра Tailwind (indigo-500 и компания),
  градиентный текст, градиентные заливки фона.
- Три AI-клише: кремовый фон + серифный дисплейный шрифт + терракота (~`#D97757`);
  почти-чёрный фон + один кислотный акцент; «газетная» вёрстка в тонкие линейки.
- Glassmorphism / матовое стекло; всё-в-карточках с мягкими тенями; бейджи-пилюли
  повсюду; скруглённое ВСЁ без меры.
- Эмодзи как иконки или заголовки разделов.
- «Атмосферный» тулкит: зерно, шум, градиентные сетки, кастомные курсоры,
  декоративные бордюры.
- Модные «характерные» дисплейные шрифты и игра пары дисплей+текст; Space Grotesk.
- **Любая декоративная анимация:** staggered-появления при загрузке, hover-флеши,
  scroll-эффекты, «красивые» переходы. В упражнении отклик **мгновенный (0–80мс)**.
- Прыгающая вёрстка (layout shift / CLS). Ноты и элементы не дёргаются.
- Модалки поверх идущего упражнения (окно, открытое во время упражнения, сначала
  останавливает его). Маркетинговые паттерны (hero-секции, «01/02/03», eyebrow-подписи),
  если они не кодируют реальную последовательность.

### Позитивные правила

- **Палитра:** светлая тёплая «бумага» (не глянцево-белая, без блика), тёмные ноты поверх,
  **ровно один спокойный акцент** — только для «эту ноту играть сейчас». Цвета — переменные в
  `src/index.css`, новых оттенков без нужды не заводить.
- **Шрифт:** один чистый читаемый UI-sans в продуманном масштабе (не модный
  дисплейный). Настоящая типографика здесь — **нотный SMuFL-шрифт (Bravura)** через
  VexFlow. Ноты и есть наш шрифт.
- **Компоновка:** один экран, **без скролла в упражнении**; ноты крупно по центру;
  управление крупное, редкое, по краям. Ландшафт основной; адаптив до телефона через
  `clamp()`, а не набор жёстких брейкпоинтов. Крупные цели **не ужимать** под телефон —
  уменьшать их количество и перекомпоновывать.
- **Тексты — с точки зрения ученика, простыми словами.** «Подключи пианино кабелем»,
  а не «MIDI device not found». Ошибка не извиняется и говорит, что делать. Кнопка
  называет действие: «Играть», не «Начать сессию». Длинные инструкции — в элемент «?»,
  а не на экран.
- **Пол по доступности:** видимый фокус клавиатуры, `prefers-reduced-motion` уважается,
  контраст AAA.
- **Все состояния, не только happy path:** у каждого экрана спроектированы пустое состояние,
  ошибка, потеря связи.

## 7. Данные на устройстве

На планшете владельца — его настоящие настройки и накопленный прогресс. Их потеря — худший
сценарий фазы развития.

| Ключ `localStorage` | Что хранит | Модуль |
|---|---|---|
| `piaono.settings.v1` | Активный режим, настройки режимов, глиссандо, выбранное устройство | `storage/settings.ts` |
| `piaono.progress.v1` | Статистика по режимам, уровни подсказок | `storage/progress.ts` |

- Новая версия **всегда читает старые данные**: новое поле отсутствует → значение по умолчанию.
- Повреждённая часть заменяется значением по умолчанию **только для этой части**, без ошибки на
  экране; остальное сохраняется.
- Запись одной части не стирает другую (читаем — заменяем своё поле — пишем).
- Несовместимая смена формата — только с новой версией ключа (`.v2`) и миграцией из старого,
  с тестом на чтение старой записи.

## 8. Соглашения по коду

- TypeScript со **строгими типами на границах** (особенно MIDI-события, модель
  упражнения, сохранённые данные). Типы документируют намерение.
- Понятные имена, небольшие функции. Комментарии там, где нужно объяснить **«почему»**,
  а не «что».
- Логика — чистые функции в `engine/` с тестами; UI — тонкий.
- Форматирование — Prettier по `.prettierrc`. Без хитрых абстракций «на вырост».

## 9. Документы и процесс

**Где что лежит:**

| Документ | Что в нём |
|---|---|
| `CLAUDE.md` | Правила проекта (этот файл). Конкретных фич здесь нет |
| `PSD/` | Бизнес-требования: спецификации компонентов, паспорта модулей (состав, статус, беклог), шаблоны. Процесс — `PSD/README.md` |
| `openspec/specs/` | Нормативный контракт реализованного поведения |
| `openspec/changes/` | Change в работе; `archive/` — история всех изменений |

Что делать дальше — беклог в паспортах модулей и новые спецификации в `PSD/`.

**Как работать со мной (правила для Claude Code):**

- **Изменение поведения начинается со спецификации в `PSD/`**, дальше — по OpenSpec:
  `/opsx:explore` → `/opsx:propose` → `/opsx:apply` → `/opsx:archive`. Код не пишем, пока
  спецификация не согласована. Итог explore и решения, принятые по ходу работы, коммитятся в
  спецификацию тем же PR; паспорт модуля обновляется вместе со спецификацией и при архивации.
- **Ветки:** `spec/<C-код>` → `propose/<change>` → `apply/<change>`, каждая от свежего `main`,
  у каждой свой PR. В `main` не отправлять и PR не сливать — сливает владелец.
- **Перед PR:** `npm run build`, `npm run lint`, `npm test`, `npm run format:check`,
  `npx openspec validate --all --strict`; изменения UI — проверка в браузере (Chromium +
  Playwright) на 1280×800 (планшет) и 740×360 (телефон).
- **PR маленький**, одна спецификация (или её часть). Описание по-русски: что сделано и
  **как проверить на планшете с пианино** (в облаке железа нет, MIDI владелец проверяет руками).
- **Тексты — только через переводы.** Любая новая функция сразу выходит на русском и английском (файлы `src/i18n/locales/ru.ts` и `en.ts`); слов в компонентах нет. Английский — язык по умолчанию и запасной. Остальные языки добавляются позже одним файлом.
- **Проход самокритики** перед сдачей: убери всё, что не служит читаемости и надёжности
  (правило «убери один аксессуар»).
- Держи дизайн-скилл (frontend-design) в режиме **строгого минимализма** по разделу 6.
  Наш фирменный элемент — **читаемость и мгновенная обратная связь**, и ничего больше.
- Перед крупным архитектурным решением или новой зависимостью — **коротко объясни и
  предложи** в описании PR, не молча.
