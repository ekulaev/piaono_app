# Design

## Context

Мотивация — proposal.md → Why. Требования — `specs/mode-menu`.

Сейчас:

- `App` держит `useExercise()` (движущаяся нота) и передаёт в `WaitingScreen` флаги
  `exerciseRunning` и `onToggleExercise`.
- «Проверка пианино» уже останавливает упражнение перед переходом.
- Настройки — `storage/settings.ts`: `{ glissando, preferredInput }` под ключом
  `piaono.settings.v1`, битые и отсутствующие поля заменяются значениями по умолчанию.
- Строка кнопок главного экрана: «Проверка пианино», «Старт/Стоп», служебные кнопки.
- На низком экране (`max-height: 30rem`) строка кнопок стоит рядом с подсказкой.

## Goals / Non-Goals

**Goals:**

- Переход меню «список ↔ экран режима ↔ закрыто» — чистая функция с тестами.
- Добавление режима «Последовательности» (этап 4) = одна запись в перечне режимов, её
  настройки и её упражнение. Меню при этом не переписывается.

**Non-Goals:**

- Настройки «Разминки»; режим «Последовательности» и его настройки (C-STF-2).
- Общая библиотека элементов настроек (переключатели, ползунки): она появится вместе с первыми
  настройками, в этапе 4. Правило NFR-1 записано в спеку уже сейчас.

## Decisions

### D1. Перечень режимов — массив в `engine/modes/modes.ts`

```ts
type ModeId = 'warmup'                  // 'sequences' добавится в этапе 4
interface ModeInfo { id: ModeId; title: string; hasSettings: boolean }
const MODES: readonly ModeInfo[] = [{ id: 'warmup', title: 'Разминка', hasSettings: false }]
const DEFAULT_MODE: ModeId = 'warmup'
```

Порядок в массиве и есть порядок в списке меню. «Последовательности» встанут первыми.
Недоступный режим в массиве отсутствует, поэтому в меню его нет (OB-14).

**Альтернатива:** флаг «доступен» у режима. Отклонена: лишнее состояние ради режима, которого
ещё нет. Правило «не на вырост» (CLAUDE.md §9).

### D2. Автомат меню — `engine/modes/modeMenu.ts`

```
closed --open--> list --choose(id)--> mode(id, draft)
  ^               |  ^                   |      |
  |    close      |  +------back---------+      | confirm / start
  +---------------+-------------------------------+
```

- `MenuState = { screen: 'closed' } | { screen: 'list' } | { screen: 'mode'; modeId; draft }`.
- Функции:
  - `openMenu`;
  - `chooseMode(state, id, confirmedSettings)` — `draft` = копия подтверждённых настроек;
  - `back` — черновик выбрасывается;
  - `closeMenu`;
  - `confirm(state)` → `{ state: closed, activeMode, settings }`.
- «Старт» в меню — это `confirm` плюс запуск упражнения в `App`.
- Тесты:
  - «Назад» не меняет активный режим и выбрасывает черновик;
  - «Выбрать» меняет активный режим;
  - закрытие ничего не меняет.

Сейчас `draft` у «Разминки» пустой. Тип настроек режима — `Record<string, never>` для
«Разминки`. «Последовательности» добавят свой тип через объединение по `ModeId`.

### D3. Хранение — поле в существующих настройках

В `Settings` добавляется `activeMode: ModeId`. Чтение: если значения нет в `MODES` (нет поля,
неизвестный режим, мусор), берётся `DEFAULT_MODE` (OB-11, OB-12). Ключ `piaono.settings.v1`
остаётся, старые данные совместимы.

Подтверждённые настройки режимов появятся в хранилище вместе с первым режимом, у которого они
есть (этап 4): у «Разминки» хранить нечего.

### D4. Панель меню — `ui/modes/ModeMenu.tsx`

- Разметка: прозрачная подложка на весь экран (`position: fixed; inset: 0`) и панель у правого
  края (`width: min(100%, clamp(20rem, 40vw, 30rem))`, на всю высоту, фон «бумага», толстая
  левая граница `--ink`).
- Подложка ловит `pointerdown`, закрывает меню и гасит событие (`preventDefault`,
  `stopPropagation`). Поэтому касание под меню не доходит до клавиатуры и кнопок (OB-13).
  Подложка прозрачная, без затемнения: затемнение снизило бы контраст экрана.
- `role="dialog"`, `aria-modal="true"`, `aria-label="Режимы"`. При открытии фокус переходит на
  первую кнопку панели. Esc закрывает меню (`keydown` на `document` пока меню открыто). При
  закрытии фокус возвращается на кнопку режима.
- Без переходов и анимаций. Панель рендерится условно (`screen !== 'closed'`).
- Список: кнопки ≥ 3.5rem. У активного режима тёмная заливка и метка «выбран» — тот же приём,
  что у выбора MIDI-устройства на «Проверке пианино».
- Экран режима: grid `auto / minmax(0, 1fr) (overflow-y: auto) / auto`. Верхняя строка и
  кнопки всегда видны (NFR-2).

**Альтернатива:** нативный `<dialog>` с `showModal()`. Отклонена: у него своя подложка
`::backdrop` и собственное поведение фокуса и Esc, а касание вне диалога по умолчанию не
закрывает его. Прозрачная подложка проще и явнее для владельца.

### D5. Встраивание в `App` и главный экран

- `App` хранит `activeMode` (из настроек) и `menu: MenuState`.
- Кнопка режима вызывает `exercise.stop()`, затем `openMenu` (OB-3).
- `onToggleExercise` запускает упражнение активного режима. Сейчас это единственное
  упражнение — `useExercise` («Разминка»). Выбор по `activeMode` делается одной веткой, этап 4
  добавит вторую.
- `WaitingScreen` получает `activeModeTitle` и `onOpenModes`; кнопка «Режим: …» стоит сразу
  после «Старт/Стоп».
- На низком экране в строке кнопок станет три кнопки. Проверяется на 740×360. Если не
  поместится, строка кнопок переносится (`flex-wrap`), а размер кнопок не уменьшается.

## Risks / Trade-offs

- **[Меню из одного пункта выглядит избыточно]** → Это сознательно: инфраструктура для этапа 4.
  Путь «выбрать → запустить» проверяется уже сейчас.
- **[Три кнопки на телефоне в ландшафте]** → Проверка раскладки в задачах. Строка кнопок может
  перенестись, и стан станет ещё ниже. Это известное ограничение телефона из этапа 3.
- **[Касание вне меню глотается]** → Так задумано (OB-13). Пианино при этом по-прежнему
  отображается на клавиатуре.
