# Design

## Context

Мотивация — proposal.md → Why. Требования — `specs/midi-input`, `specs/connection-status`.

Сейчас `startMidiMonitor(callbacks)` в `src/midi/midiAccess.ts`:

- на каждом `statechange` и при `visibilitychange → visible` перечитывает входы и вешает
  `onmidimessage` на **все** подключённые;
- сообщает `onConnectionChange(state, devices)` и `onNoteEvent(event)`;
- разбор сообщения (`buildNoteEvent`) — внутренняя функция.

`App` владеет подпиской и при любом состоянии, кроме `connected`, вызывает
`pianoReset` движка клавиатуры, чтобы не оставались зажатые клавиши. Тестов у `midi/` нет.

## Goals / Non-Goals

**Goals:**

- Правило выбора входа и разбор сообщений — чистые функции с юнит-тестами.
- Весь сценарий «подключили / выдернули / выбрали / уснули» проверяется тестом
  с подменённым Web MIDI, без браузера.
- Интерфейс `midi/` меняется минимально: те же колбэки, плюс активный вход и метод выбора.

**Non-Goals:**

- Шина событий и несколько подписчиков: потребитель один (`App`).
- MIDI-выход, педали, выбор MIDI-канала.
- Автоопределение «виртуальных» портов по имени.

## Decisions

### D1. Выбор входа — чистая функция

`src/midi/inputChoice.ts`:

```ts
interface PreferredInput { id: string; name: string }
chooseActiveInput(inputs: MidiDeviceInfo[], preferred: PreferredInput | null): string | null
```

Логика по шагам:

1. Входов нет — вернуть `null`.
2. Предпочтённый вход найден по `id` — вернуть его.
3. Не найден по `id`, но найден по `name` — вернуть его.
4. Иначе вернуть первый вход.

Порядок — тот, в котором браузер перечисляет `access.inputs`.

**Альтернатива:** запоминать только имя. Отклонена: у двух одинаковых устройств имена
совпадают, а `id` их различает. Поиск по имени остаётся запасным.

### D2. Разбор сообщения — отдельная экспортируемая функция

`src/midi/messages.ts` → `parseMidiMessage(data, time): MidiNoteEvent | null`. Внутренняя
`buildNoteEvent` переезжает сюда без изменения логики, но с одной добавкой: первый байт
должен быть статусным (≥ 0x80), а длина сообщения — ровно 3 байта для note-on и note-off.
Всё остальное → `null`.

### D3. Монитор: один активный вход, память о зажатых нотах

`startMidiMonitor(callbacks, { preferred })` возвращает `{ stop, retry, selectInput }`.
Колбэк связи — `onConnectionChange(state, devices, activeId)`.

```
 statechange / visible / selectInput
             |
             v
        sync(access)
             |
   inputs = connected inputs
   nextId = chooseActiveInput(inputs, preferred)
             |
   nextId != activeId ? --да--> releaseHeld()   (NoteOff для каждой зажатой ноты)
             |                   detach старый вход
             |                   attach новый: onmidimessage + open().catch()
             v
   onConnectionChange(state, devices, activeId)
```

- Слушается только активный вход. Если активный не сменился, обработчик всё равно
  переустанавливается и `open()` вызывается снова. Это и есть «переоткрыть после сна»: дёшево
  и безопасно.
- `held: Set<number>` — ноты, нажатые на активном входе и ещё не отпущенные. `releaseHeld()`
  отправляет для каждой `NoteOff { pitch, time: performance.now() }` и очищает множество.
  Вызывается при смене активного входа, при его пропаже и в `stop()`.
- Вызов колбэка ноты обёрнут в `try/catch`: исключение потребителя не ломает приём.
- `selectInput({ id, name })` меняет предпочтение в памяти модуля и делает `sync`.
  Сохранять выбор между запусками — забота `App` (через `storage/`), а не `midi/`: слой железа
  не знает про `localStorage`.

**Альтернатива:** отпускать зажатые ноты в `App` (как сейчас `pianoReset`). Отклонена:
только `midi/` знает, какой вход активен и что на нём нажато. Иначе правило размазано по двум
слоям.

### D4. Удаление `pianoReset`

Вход `pianoReset` из `engine/keyboard` и его вызов в `App` удаляются вместе с тестом. Теперь
модуль присылает обычные отпускания. Движок получает меньше особых случаев, а «пианино
главнее касания» работает и для синтетических отпусканий.

### D5. Хранение выбора

В `Settings` добавляется `preferredInput: { id, name } | null` (по умолчанию `null`).
Ключ остаётся `piaono.settings.v1`: старые данные без поля читаются, поле получает значение
по умолчанию. Некорректное значение (не объект, нет строк `id`/`name`) даёт `null`.
`App` хранит настройки целиком и сохраняет их при изменении глиссандо и при выборе входа.

### D6. Тесты с подменённым Web MIDI

`src/midi/midiAccess.test.ts` через `vi.stubGlobal` подменяет `navigator.requestMIDIAccess`
и `document` (`visibilityState`, `add/removeEventListener`). Фейковый `MIDIAccess` — это
`Map` входов, `onstatechange` и методы теста: `connect`, `disconnect`, `send`. Проверяются
сценарии спеки `midi-input`: один вход, два входа, предпочтение по `id` и по имени, пропажа
и возврат, отпускание зажатых нот, `open()` с отказом, ошибка в обработчике, видимость.

### D7. Интерфейс

- «Проверка пианино»: строки списка становятся `button` (≥ 3.5rem). У активной — тёмная
  заливка и метка «слушаю» справа. Касание вызывает `onSelectDevice`.
- Экран ожидания в состоянии «на связи»: имя активного устройства; при `devices.length > 1`
  под именем подсказка «Устройств несколько — выбрать можно в „Проверке пианино“».

## Risks / Trade-offs

- **[`id` входа на Android меняется после переподключения]** → поиск по имени (D1).
  У двух одинаковых устройств после переподключения может выбраться не то. → Оно видно по
  имени на экране и меняется одним касанием.
- **[Автопереключение на оставшийся вход может «подсунуть» не то устройство]** → Так
  выбрано ради приоритета №1. Имя активного устройства всегда на экране. Предпочтение
  не стирается, поэтому при возвращении выбранного входа всё вернётся само.
- **[Повторный `open()` на каждом `statechange`]** → Для открытого порта это пустая операция
  по спецификации Web MIDI. Отказ глушится.
