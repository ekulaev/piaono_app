# Design

## Context

Мотивация — см. proposal.md → Why. Требования — см. `specs/pwa-shell` и `specs/connection-status`.

Текущее состояние (после этапа 0):
- Vite 8 + React 19 + TypeScript, сборка с `base: '/piaono_app/'`, деплой GitHub Actions → Pages.
- `src/midi/midiAccess.ts` — `startMidiMonitor(callbacks)`: запрос доступа, подписка на все
  входы, переподписка на `statechange`, разбор note-on/off (velocity 0 = note-off).
  Состояния: `unavailable | connecting | no-device | connected`. Любой отказ
  `requestMIDIAccess` сейчас превращается в `unavailable` — «не поддерживается»
  и «запрещено» неразличимы. Потерю связи тоже нельзя отличить от «ещё не подключали».
- `src/ui/App.tsx` — единственный экран (монитор), подписывается на MIDI в `useEffect`.
- Service worker и манифеста нет. Тестового фреймворка нет.

Ограничения: CLAUDE.md (приоритеты, дизайн-конституция, запрет модалок и декоративной
анимации, минимум зависимостей).

## Goals / Non-Goals

**Goals:**
- Установка и офлайн-работа стандартными средствами экосистемы Vite, без ручного service worker.
- Модель состояний связи в `midi/`, достаточная для шести состояний экрана.
- Один экран ожидания + диагностический экран без роутера.

**Non-Goals:**
- Выбор устройства при нескольких MIDI-входах, событийная шина `midi/` — этап 2.
- Слой `engine/` — появится вместе с логикой упражнений (этап 4); пустой слой «на вырост»
  не создаём.
- Push-уведомления, фоновая синхронизация, кэширование внешних ресурсов (их нет).
- Тёмная тема, фиксация ориентации экрана.

## Decisions

### D1. `vite-plugin-pwa` в режиме `generateSW` (Workbox)
Плагин генерирует манифест и service worker с precache всех собранных файлов и учитывает
`base`. **Альтернативы:** ручной service worker — много тонкого кода про версии кэша, ровно
тот велосипед, который не нужен; `injectManifest` — нужен только для своей логики SW,
которой у нас нет. Плагин уже заявлен в стеке CLAUDE.md, совместим с Vite 8.

### D2. Обновления: `registerType: 'prompt'`, без автоперезагрузки
Новый SW скачивается в фоне и ждёт. Применяется при следующем запуске (когда закрыты все окна
приложения) либо по кнопке «Обновить сейчас». Кнопку даёт хук `useRegisterSW`
из `virtual:pwa-register/react` (`needRefresh`, `updateServiceWorker(true)`).
**Альтернатива:** `autoUpdate` — проще, но перезагружает страницу сам, в будущем посреди
упражнения. Это нарушает «никаких модалок/прерываний поверх упражнения».
Кнопка — обычная кнопка у края экрана ожидания, не баннер поверх контента, не модалка.

### D3. Манифест
`name: "Нотный тренажёр"`, `short_name: "Ноты"`, `lang: "ru"`, `id/start_url/scope: "/piaono_app/"`,
`display: "standalone"`, `background_color` и `theme_color` = `#f3ede0` («бумага» из
`index.css`). **Ориентацию не фиксируем:** ландшафт — основной сценарий, но CLAUDE.md требует
адаптив до телефона; блокировка сломала бы портрет на телефоне.

### D4. Иконки: один SVG-источник → PNG разовой генерацией
Исходник `public/pwa-icon.svg` (простая знаковая форма в палитре приложения, без мелких
деталей). PNG 64/192/512, maskable 512 и apple-touch-icon генерируются один раз командой
`npx @vite-pwa/assets-generator@1 --preset minimal-2023 public/pwa-icon.svg` и коммитятся.
Генератор не попадает в `package.json` — не нужен при каждой сборке.
**Альтернатива:** рисовать PNG руками — легко ошибиться с безопасной зоной maskable-иконки.

### D5. Модель состояний в `midi/`
`ConnectionState = 'unsupported' | 'permission-denied' | 'connecting' | 'no-device' | 'connected' | 'lost'`.
- `unsupported` — нет `navigator.requestMIDIAccess`.
- `permission-denied` — `requestMIDIAccess` отклонён (обычно `SecurityError`/`NotAllowedError`;
  прочие ошибки показываем так же — у пользователя одно и то же действие: разрешить и повторить).
- `lost` — в этой сессии устройство уже было, а сейчас входов нет. Флаг «уже было» живёт
  в `midi/`: это знание о соединении, не об интерфейсе.
- `startMidiMonitor` возвращает объект `{ stop, retry }`; `retry()` повторяет запрос доступа
  без перезагрузки страницы.
**Альтернатива:** вычислять `lost` в UI — размазывает логику связи по слоям, против раздела 4.

### D6. Ресинхронизация при возвращении на экран
Дополнительно к `statechange` при `visibilitychange → visible` `midi/` заново читает список
входов и переподписывается. Цена — несколько строк; страховка на случай, если какая-то сборка
Android пропустит `statechange` после сна (надёжность — приоритет №1). Повторный запрос
доступа при этом не делается.

### D7. Два экрана без роутера
`App` хранит `screen: 'waiting' | 'check'` и владеет единственной подпиской на MIDI; оба экрана
получают состояние через props. Переключение экранов не трогает соединение. Журнал нот
(до 100 записей) хранится в `App`, чтобы не терялся при переходах.
**Альтернатива:** React Router — лишняя зависимость ради двух экранов.

### D8. Экран ожидания
Крупный индикатор состояния (форма + текст, как в мониторе этапа 0 — токены из `index.css`
переиспользуются), под ним подсказка «что делать» для текущего состояния, в состоянии
«на связи» — имя последней ноты самым крупным текстом (`clamp()` от ~6rem). Кнопки
«Проверка пианино», «Попробовать снова» (только в `permission-denied`), «Обновить сейчас»
(только при `needRefresh`) — у края экрана, высота ≥ 3.5rem. Без анимаций; смена состояния
мгновенная. Раскладка фиксирована, чтобы смена текста не вызывала скачков (CLS).

## Risks / Trade-offs

- [SW закэшировал старую версию, владелец не видит исправление] → кнопка «Обновить сейчас»
  появляется сразу, как новая версия скачана; precache Workbox версионирует файлы по хэшу.
- [Установленное приложение на Android почти никогда не «закрывается» полностью, обновление
  при следующем запуске откладывается] → та же кнопка на экране ожидания.
- [Неверная область SW из-за `base`] → проверка в DevTools → Application: scope = `/piaono_app/`.
- [Откат: если просто убрать плагин, старый SW останется у пользователя и продолжит отдавать
  закэшированную оболочку] → откат делаем выкладкой версии с `selfDestroying: true`
  в настройках плагина, а не удалением плагина.
- [Разные ошибки `requestMIDIAccess` сведены в `permission-denied`] → действие для пользователя
  одно («разрешить и повторить»); текст сформулирован так, чтобы подходить к обоим случаям.
- [Нет автотестов] → проверка через сборку, headless Chromium с подменённым Web MIDI (как в
  этапе 0) и ручной чек-лист на планшете. Фреймворк тестов добавим вместе с логикой `engine/`.

## Migration Plan

1. Мерж PR в `main` → существующий workflow собирает и публикует на Pages.
2. Первое открытие на планшете регистрирует SW; дальше — установка на главный экран.
3. Откат — см. риск про `selfDestroying` выше.
