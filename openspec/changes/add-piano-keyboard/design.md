# Design

## Context

Мотивация — см. proposal.md → Why. Требования — см. `specs/piano-keyboard`
и `specs/connection-status`.

Текущее состояние (после этапа 1):

- `src/midi/midiAccess.ts` — `startMidiMonitor(callbacks)` отдаёт шесть состояний связи
  и события `noteOn { pitch, velocity, time }` / `noteOff { pitch, time }`.
- `src/ui/App.tsx` держит единственную подписку на MIDI, журнал для «Проверки пианино»
  и `lastNoteName`, а также переключает экраны `waiting | check`.
- `WaitingScreen` — сетка из трёх рядов на `100svh`: индикатор, середина, кнопки.
  `body` имеет `min-height: 100svh`, поэтому прокрутка страницы не запрещена явно.
- В манифесте нет `orientation`: в прошлом design (D3) ориентацию сознательно не фиксировали.
- Слоя `engine/` пока нет. Тестового фреймворка нет.

## Goals / Non-Goals

**Goals:**

- Вся логика клавиатуры — чистые функции в `engine/keyboard`, покрытые юнит-тестами
  по сценариям спеки.
- Отклик ≤ 50 мс: от события до отрисовки один синхронный проход без анимаций.
- Слой `midi/` не меняется.

**Non-Goals:**

- Звук, педали, подписи нот, масштабирование клавиатуры пользователем.
- Экран настроек (переключатель глиссандо временно стоит на «Проверке пианино»).
- Подсказки на клавиатуре («эту ноту играть сейчас») — появятся с упражнениями.
- Выбор устройства при нескольких MIDI-входах.

## Decisions

### D1. Источник ноты появляется только в `engine/`

`engine/keyboard/types.ts` определяет вход движка:

```ts
type KeyInput =
  | { kind: 'pianoDown'; pitch: number; velocity: number }
  | { kind: 'pianoUp'; pitch: number }
  | { kind: 'touchDown'; pointerId: number; pitch: number; pressure: number }
  | { kind: 'touchMove'; pointerId: number; pitch: number | null } // палец над другой клавишей
  | { kind: 'touchUp'; pointerId: number }
```

`App` переводит события `midi/` в `pianoDown/pianoUp`, клавиатура в `ui/` переводит
Pointer Events в `touch*`.

```
  midi/ --noteOn/noteOff--> App --pianoDown/Up--+
                                                +--> engine/keyboard (reducer) --> KeyboardState --> ui/keyboard
  ui/keyboard --pointer events--> touch* -------+                    |
                                                                     +--> playedNote --> lastNoteName
```

**Альтернатива:** добавить поле `source` в типы `midi/`. Отклонена, потому что `midi/`
по контракту знает только сырой MIDI, а касание к нему не относится.

### D2. Модель состояния клавиши: два независимых источника

```ts
interface KeyboardState {
  piano: Map<number, number>          // pitch (0..127) -> velocity; удерживается на пианино
  touches: Map<number, TouchHold>     // pointerId -> { pitch, level, cancelled }
  glissando: boolean
}
```

Выводимые значения — чистые функции от состояния:

- `isPressed(pitch)` = `piano.has(pitch)` или есть касание этой клавиши с `cancelled = false`.
- `levelOf(pitch)` = уровень пианино, если клавиша удерживается на пианино, иначе
  уровень касания.
- `heldPitches()` = ключи `piano` плюс высоты живых касаний. Отсюда же считается подсветка
  кнопок (D5).

Переходы:

- `pianoUp` удаляет высоту из `piano` и ставит `cancelled = true` всем касаниям этой высоты.
  Это реализует требование «Пианино главнее касания»: строки 2, 3 и 5 таблицы.
- `touchUp` удаляет только своё касание, поэтому клавиша, которую держит пианино, остаётся
  нажатой (строка 1).
- `touchMove`: при выключенном глиссандо игнорируется; при включённом, если высота
  изменилась, касание переезжает на новую клавишу с новым `playedNote`.

Редьюсер `reduce(state, input) → { state, playedNote | null }` возвращает сыгранную ноту
при каждом `pianoDown`, `touchDown` и при глиссандо-переходе, даже если клавиша уже нажата.
Это требование «Касание — полноценная сыгранная нота».

**Альтернатива:** одно поле `pressed: boolean` на клавишу с правилом «последнее событие
побеждает». Отклонена: оно не выражает строку 1 (отпускание пальца при удержанном пианино).

### D3. Уровни интенсивности

- `levelFromVelocity(v)`: 1–42 → 1, 43–84 → 2, 85–127 → 3.
- `levelFromPressure(p)`: `p === 0 || p === 0.5` → 2 (датчика нет); `p ≤ 1/3` → 1;
  `p ≤ 2/3` → 2; иначе 3.

У пианино, которое не передаёт силу, velocity фиксированная (обычно 64 или 100). Отличить
его от «настоящей» силы нельзя, поэтому отдельного случая нет: такое пианино даёт всегда
один уровень. Это соответствует OB-26 для практически всех инструментов, потому что
фиксированное значение 64 и есть уровень 2.

### D4. Геометрия: целое число видимых белых клавиш

`engine/keyboard/layout.ts`:

```ts
computeLayout(zoneWidthPx, remPx) -> {
  whiteWidthPx, blackWidthPx, visibleWhiteCount, showButtons
}
```

- Минимальная белая = `3.5rem / 0.58`.
- Если `52 × минимальная белая ≤ zoneWidth`, видны все клавиши, `whiteWidth = zoneWidth / 52`,
  кнопок нет.
- Иначе `visibleWhiteCount = floor((zoneWidth − 2 × минимальная белая) / минимальная белая)`,
  и белые растягиваются так, чтобы ровно заполнить место между кнопками. Кнопки имеют ширину
  белой клавиши. Обрезанных клавиш по краям нет.
- `blackWidth = whiteWidth × 0.58`.

Окно видимой части — индекс первой видимой белой клавиши `whiteStart` (0 = A0). Функции:

- `initialStart(count)`: C4 в центре.
- `resize(start, oldCount, newCount)`: центральная белая остаётся в центре, затем значение
  прижимается к `[0, 52 − count]`.
- `shift(start, ±1, count)`.
- `isBlocked(side)`.

Чёрная клавиша видима, только если видимы обе её белые соседки. Чёрная клавиша у края окна
не рисуется и считается скрытой.

Геометрия лежит в `engine/`, потому что это чистая арифметика без React. Так её проще
тестировать и читать.

**Альтернатива:** горизонтальный скролл-контейнер с дробным количеством клавиш. Отклонена:
у скролл-контейнера есть инерция и жесты браузера, а прокрутка жестом отменена.

### D5. Подсветка кнопок — вычисление, а не событие

`scrollHints(heldPitches, visibleRange) → { left: boolean, right: boolean }`, где
`visibleRange` — высоты от первой до последней видимой белой клавиши. Функция вызывается
на каждой отрисовке. Состояния «подсвечено» нигде не хранится, поэтому рассинхронизироваться
ему не с чем. Ноты 0–20 и 109–127 попадают в `piano` как обычные и сами дают подсветку.

### D6. Отрисовка: DOM, абсолютное позиционирование, попадание — по геометрии

- Клавиши — `div` с `position: absolute` по координатам из D4. Кнопки прокрутки — `button`.
- Без переходов и анимаций. Нажатие меняет классы: `key--pressed`, `key--level-1..3`.
- Все обработчики висят на зоне клавиатуры (`onPointerDown/Move/Up/Cancel`) с
  `setPointerCapture`. Клавиша под пальцем определяется функцией
  `hitTest(x, y, layout, start)`: чёрные клавиши лежат поверх белых в верхних 62 % высоты.
  Эта функция тоже в `engine/keyboard`, поэтому поведение пальца на границе клавиш
  покрыто тестами, а не зависит от DOM.
- На зоне `touch-action: none` и `overscroll-behavior: none`: браузер не забирает жест
  (pull-to-refresh, прокрутку), а Pointer Events приходят непрерывно.

**Альтернативы:**

- Canvas — быстрее при тысячах объектов, но у нас 88 элементов. Canvas хуже читается
  владельцем и теряет доступность.
- SVG — сопоставим с DOM, но стили нажатия сложнее.
- VexFlow здесь не нужен: он для нот, а не для клавиатуры.

### D7. Автоповтор кнопок

Функция `repeatDelayMs(heldMs) = max(100, 500 − 100 × floor(heldMs / 1000))` лежит
в `engine/keyboard`. В `ui/` хук держит цепочку `setTimeout`:

- `pointerdown` — сразу `shift` и планирование следующего сдвига;
- `pointerup`, `pointercancel`, `lostpointercapture` или блокировка — остановка.

`setInterval` не используется, потому что интервал меняется.

### D8. Настройки: типизированная обёртка над `localStorage`

`src/storage/settings.ts`:

- `loadSettings(): Settings` — `{ glissando: false }` по умолчанию; битые или
  отсутствующие данные дают значения по умолчанию;
- `saveSettings(s)`.

Используется ключ `piaono.settings.v1`, запись и чтение обёрнуты в `try/catch`, потому что
приватный режим или переполненная квота не должны ронять приложение. Других обращений
к `localStorage` в коде нет. Это та обёртка, которую CLAUDE.md §9 требует с первого
использования. Этап 6 расширит её, а не заменит.

### D9. Экран без прокрутки

- `html, body { height: 100%; overflow: hidden; }`.
- `WaitingScreen` становится сеткой из четырёх рядов:
  `auto` индикатор · `1fr` середина · `auto` кнопки · зона клавиатуры
  `max(25svh, 8rem)`, без `max-width` у ряда клавиатуры.
- Середина получает `overflow-y: auto` и `min-height: 0`: на телефоне прокручивается только
  подсказка.
- Размер крупного имени ноты ограничивается и высотой середины, а не только `22vh`,
  чтобы не выталкивать кнопки.

### D10. Ориентация: `orientation: 'landscape'` в манифесте

Chrome применяет эту настройку только к установленному приложению (`display: standalone`).
Во вкладке браузера она игнорируется, и там работает адаптивная раскладка (OB-29). Это
пересматривает D3 из `add-pwa-shell`: тогда мы не фиксировали ориентацию ради портрета
на телефоне, теперь портрет остаётся только во вкладке.

**Альтернатива:** `screen.orientation.lock()`. Отклонена: работает только в полноэкранном
режиме и требует жеста пользователя.

### D11. Vitest для `engine/`

Новая devDependency `vitest`. Обоснование:

- Логика двух источников и геометрии содержит граничные случаи, которые вручную
  на планшете не перебрать.
- Каждый сценарий спеки превращается в тест, и это проверка SDD-подхода.
- Vitest использует конфигурацию Vite, отдельный конфиг не нужен. Окружение `node` —
  тестируются только чистые функции, поэтому jsdom и Testing Library не нужны.

Скрипт `npm test` = `vitest run`.

**Альтернатива:** встроенный `node --test`. Он потребовал бы отдельной компиляции TS
или флагов загрузчика, а это хуже читается.

### D12. Цвета клавиш (стартовые, калибруются на планшете)

- Белая клавиша — «бумага» `--paper`. Чёрная — `--ink`.
- Нажатая белая — `--ink-soft` (#4a4032, контраст с соседними белыми ≈ 9:1).
- Нажатая чёрная — `#5c4f3c`: светлее чёрной, контраст с соседними белыми ≥ 7:1.
  От ненажатой чёрной нажатая отличается прежде всего формой: смещением лицевой части
  и полосой тени.
- Полоса тени — сплошная `--ink` без размытия, толщина 0.25 / 0.5 / 0.75rem по уровням.
  Смещение лицевой части — 0.25 / 0.5 / 0.75rem.
- Подсвеченная кнопка прокрутки — заливка `--ink-soft` и светлая стрелка.
- Акцент `--accent` на клавиатуре не используется.

## Risks / Trade-offs

- **[Системный жест «назад» Android от края экрана]** Это жест ОС, веб-страница его не
  перехватывает. Кнопки прокрутки стоят у краёв. → Касание кнопки жестом ОС не считается,
  только свайп от самой кромки. Владелец проверяет это на планшете (чек-лист в PR). Если
  мешает, добавить внешний отступ зоны.
- **[Установленное приложение не сразу подхватит `orientation`]** Chrome обновляет
  WebAPK по своему расписанию. → В чек-листе PR: если поворот ещё работает, переустановить
  приложение с главного экрана.
- **[Задержка касания]** React-перерисовка на каждое событие. → Состояние маленькое
  (88 клавиш), компонент клавиши мемоизирован по `(pressed, level)`. В чек-листе PR —
  проверка на глаз одновременно с пианино. Если отклик заметен, обновлять клавиши
  через ref без React-рендера.
- **[На планшете видно ~1,6 октавы]** Это прямое следствие чёрной клавиши 3.5rem —
  решение владельца. → Кнопки с автоповтором проходят весь диапазон примерно за 5 с.
- **[Нажатая чёрная близка к ненажатой по цвету]** → Различие несут форма и полоса тени
  (требование «заливка + форма»). Цвета финально калибруются на планшете.
- **[Касание по экрану вводит в заблуждение, будто пианино работает]** → Крупное имя ноты
  показывается только в «Пианино на связи». Индикатор связи касанием не меняется.

## Migration Plan

Данных для миграции нет: `localStorage` раньше не использовался. Откат — revert PR.
Установленное приложение получит новую версию через обычную кнопку «Обновить сейчас».

## Open Questions

- Финальные цвета нажатых клавиш и толщины полос тени — после проверки на планшете владельца.
  На спеки и задачи не влияют.
